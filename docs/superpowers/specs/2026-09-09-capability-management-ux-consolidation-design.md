# 能力接入管理体验收口设计

**日期：** 2026-09-09

## 1. 目标

本轮目标是降低第一次接入能力的学习成本，并让页面状态、试调结果和发布动作可信一致。用户不需要理解 `Capability`、`source`、`probe` 或 `governance` 等内部术语，也能完成：

```text
输入接口 → 验证接口 → 确认 AI 工具 → 发布给 AI
```

本轮只做前端体验和已确认的状态逻辑修正，不改变能力运行时架构、权限模型或安全出站策略。

## 2. 范围

### 2.1 主流程

将用户可见步骤展示为：

1. **连接接口**：输入一个完整接口地址，或导入 Swagger/OpenAPI。
2. **验证接口**：确认测试参数并执行真实试调；写入接口不执行真实请求，只生成草稿。
3. **确认工具**：确认工具名称、用途、输入参数和输出信息。
4. **发布给 AI**：查看发布摘要并发布，发布后可直接发起一次 AI 验证。

内部 `ManagementPhase` 可以继续复用现有实现，但 WorkflowRail、阶段标题、按钮和状态文案统一使用上述用户语言。

### 2.2 接入口收口

Source 阶段默认只展示两个入口：

- **接入一个接口**（推荐）
- **批量导入 Swagger / OpenAPI**

高级 JSON、快速发布、手写草稿、字段映射和执行保护配置收进“高级设置”折叠区。移除或替换 Source 阶段永久禁用的“生成 Capability 草稿”控件。

单接口入口继续支持完整 URL 拆分为 `base_url + path`。Swagger 入口增加清晰说明：文档地址用于读取接口定义，实际调用地址用于执行接口；如果两者相同，提供“一致”选项减少重复填写。

### 2.3 状态模型

用户界面只显示以下状态：

| UI 状态 | 含义 |
| --- | --- |
| 草稿 | 已保存但尚未完成必要配置 |
| 待验证 | 定义完整，尚未通过真实试调 |
| 可发布 | 校验和必要试调均通过 |
| 已发布 | AI 当前可以使用 |

内部 `source` 和 `status` 仍由后端保留，但所有列表统计、筛选、卡片标签和下一步动作必须由同一套前端映射产生。特别要修复“顶部草稿数量为 0、列表实际存在草稿”的矛盾。

“当前可发布 N 个”表示数量，不使用“已选”措辞；真正的批量选择应单独显示“已选择 N 个”。

### 2.4 导入与试调

候选页只保留一个主提交动作，按钮文案动态反映真实行为，例如：

```text
导入 4 个接口，自动发布其中 3 个
```

按钮下明确说明：读取接口会进行一次真实试调；写入接口不会自动调用，只保存为草稿。

试调结果按以下信息展示：

- 已验证通过数量
- 需要人工处理数量
- 未试调的写入接口数量
- 当前试调批次对应的 Swagger 来源

重新预览或切换 Swagger 时，必须清空旧候选的试调结果、进度、导入批次和筛选状态。试调结果使用候选 ID 关联，不能依赖用户可修改的能力名称。改名、改描述不应丢失验证关联；修改请求路径或 HTTP 方法后应要求重新验证。

自动发布资格必须基于提交后的最终候选定义，而不是试调前的原始名称、操作类型或风险等级。

### 2.5 评审与发布

每个能力详情页只突出一个“下一步”动作：

- 补充接口信息
- 填写测试参数
- 开始真实试调
- 补充工具说明
- 发布给 AI

发布检查表和清单卡片必须使用同一套发布资格判断。不可执行的动作不显示，草稿不显示“下线”，已发布能力不显示“删除草稿”。

发布前展示确认摘要：

- 工具名称和用途
- HTTP 方法与路径
- 输入参数
- 输出字段/摘要
- 试调结果
- 当前发布范围

发布成功后提供“用 AI 试问一次”和“继续接入下一个”两个后续动作。AI 预检若跳转到助手视图，应根据结果类型处理，不应无条件切走导致用户失去上下文。

### 2.6 术语和布局

主流程使用用户语言：

| 工程术语 | 主界面文案 |
| --- | --- |
| Capability | AI 工具 |
| Probe | 真实试调 |
| Enrich | AI 补全说明 |
| Output Mapping | 输出字段 |
| Governance | 执行保护 |
| Precheck | 执行前检查 |
| Rollback | 失败恢复 |
| AI Preflight | 发布后验证 |

技术字段放进高级设置或帮助提示。

响应式布局：

- 宽屏：能力清单 + 详情/向导双栏。
- 中等宽度：能力清单可折叠，保证详情最小可用宽度。
- 窄屏：能力清单和详情上下排列。

不能让固定宽度的左栏挤压右侧到无法填写表单的程度。

## 3. 组件和数据流

### 3.1 组件职责

- `ManagementView`：承载四步流程和入口切换，不重复渲染状态提示。
- `CapabilityLedgerPanel`：展示统一状态、筛选、数量和当前能力动作。
- `SourceStage`：只负责两种接入入口与高级设置。
- `CandidatesStage`：展示候选、选择、必要调整、批量试调和单一提交动作。
- `ReviewStage`：展示能力详情、测试、真实试调、确认摘要和发布动作。
- `useCapabilityImport`：维护导入批次、候选选择、试调状态，切换批次时完整清理状态。
- `useCapabilityPublish` / `useCapabilityEditor`：共享发布资格和下一步动作计算，不各自复制规则。

### 3.2 状态清理规则

每次开始新的 Swagger 预览时：

```text
importPreview = null
candidateSelections = {}
candidateOverrides = {}
candidateProbeResults = {}
candidateProbedProgress = 0
importBatch = null
候选筛选 = 默认值
```

新的导入批次必须拥有独立的批次来源标识。旧批次的结果不得参与新批次的可发布计算。

## 4. 错误处理

错误提示必须同时包含：

1. 用户能理解的原因；
2. 对当前流程的影响；
3. 可执行的下一步。

例如：

```text
接口返回 404，暂时无法验证。
草稿仍可保存，但不会自动发布。
请检查实际调用地址或修改接口路径。
```

批量导入部分成功时，明确区分：

- 成功保存的草稿
- 自动发布成功的能力
- 自动发布失败的能力及原因
- 未选择或未试调的能力

## 5. 验收标准

### 功能

- 首次打开页面能明确看到“接入一个接口”和“批量导入 Swagger”两个入口。
- Source 阶段不存在永久禁用且无后续作用的提交按钮。
- 内置示例能完成预览，候选页只显示一个真实提交主动作。
- 导入、试调、发布后的数量和状态与列表内容一致。
- 切换 Swagger 后，新候选不显示旧批次试调结果。
- 候选改名后，已通过试调的候选仍能正确关联并按最终定义决定是否自动发布。
- 发布清单和列表对同一能力给出一致的可发布结论。
- 草稿、待验证、可发布、已发布状态和动作符合状态模型。

### 体验

- 用户不阅读工程文档，也能理解下一步要做什么。
- 主界面不要求用户先理解 JSONPath、source 或 governance。
- 窄窗口下表单仍可读、可填写、可提交。
- 真实试调发生前，用户能看到会请求哪些接口以及写接口不会被调用。

### 测试

补充或更新：

- `useCapabilityImport.test.ts`：切换批次状态清理、进度重置、改名关联、最终 override 参与自动发布。
- `useCapabilityPublish.test.ts` 或现有发布测试：统一发布资格规则和用户状态映射。
- `SourceStage.test.ts` / `CandidatesStage.test.ts` / `ReviewStage.test.ts`：入口数量、主按钮文案、状态动作。
- `ManagementView.test.ts`：四步文案和窄屏相关结构不回退。
- 浏览器验证：页面加载、内置示例预览、选候选、真实试调、错误提示和响应式布局。

## 6. 非目标

本轮不处理：

- SSRF、出站白名单和其他安全加固；
- 多节点发布事务和运行时对账；
- 依赖链治理；
- 新权限模型；
- 能力 YAML 数据模型重构；
- 全量视觉重设计。
