# 中间件管理后台 AI 化设计

## 1. 目标与边界

将已有中间件运维 API 封装为安全、可审计的 AI 运维副驾驶。第一期同时支持：

- 自然语言查询、告警解释与排障建议；
- 由 AI 生成、用户确认后执行的低风险运维操作。

现有平台已经具备认证、RBAC 与操作审计；API 提供 OpenAPI/Swagger 描述，且能区分查询与变更接口。所有第一期变更都必须人工确认。系统不绕过既有身份、权限或审计机制。

## 2. 总体架构

```text
Web 管理后台（对话、计划预览、审批、结果）
                |
                v
AI 编排服务（意图识别、工具选择、上下文组装、结果总结）
       |                         |
       v                         v
知识检索服务                 工具注册表
（手册、Runbook、案例）      （由 OpenAPI 生成的受限 API 工具）
       |                         |
       +-----------+-------------+
                   v
策略执行网关（身份透传、RBAC、参数模式校验、风险分级、限流、幂等）
                   |
         查询直接返回 / 变更生成计划
                            |
                            v
                 人工确认与审批记录
                            |
                            v
                  既有运维 API 与审计系统
```

AI 编排服务只能请求工具注册表中暴露的能力，不能直接访问内网、数据库或原始 API。策略执行网关是唯一调用运维 API 的路径，并使用发起用户的身份和权限上下文完成二次校验。

## 3. 关键组件与职责

### 3.1 AI 编排服务

- 判断请求是查询、分析、生成计划还是执行已确认计划。
- 调用只读工具获取事实，结合检索到的 Runbook 给出带证据的结论。
- 对变更请求只生成结构化计划，绝不在同一轮对话中自动执行。
- 输出固定结构：目标、范围、证据、操作步骤、风险、回滚、待确认动作和结果。

### 3.2 工具注册表

- 从 OpenAPI/Swagger 自动生成候选工具，但以人工维护的 allowlist 作为实际暴露集合。
- 每项工具标记 `read` 或 `write`、资源范围、风险级别、是否可回滚、是否要求幂等键，以及参数 JSON Schema。
- 将原始 API 名称替换为面向任务的工具名，例如 `get_redis_memory_hotspots`、`create_kafka_topic_expansion_plan`。

### 3.3 策略执行网关

- 透传用户身份，并用既有 RBAC 再次校验资源、环境和动作权限。
- 校验模型产生的参数是否符合 Schema、环境是否允许、目标数量是否超过阈值。
- 为写操作创建不可篡改的计划快照；确认时仅执行该快照，禁止模型在确认后重新改写参数。
- 执行时使用幂等键、超时、限流和可选的 dry-run；写入统一审计事件。

### 3.4 知识检索服务

- 纳入 API 文档、服务拓扑、Runbook、SOP、故障复盘和告警说明；每条文档含版本、服务、环境与生效时间。
- 先做关键字与向量混合检索，再让模型基于检索结果回答，并在界面展示引用依据。
- 运行记录与聊天记录分开保存；敏感字段在进入模型前脱敏。

### 3.5 管理后台交互

- 查询结果展示来源、时间范围和 API 返回摘要。
- 变更卡片必须展示影响对象、精确参数、前置检查、风险等级、回滚方案与审批人。
- 用户可编辑受允许的参数；任何编辑均触发重新校验与新的计划快照。
- 结果页展示每一步状态、原始 API 关联 ID、失败原因与后续建议。

## 4. 安全和风险控制

| 风险等级 | 示例 | 第一期处理方式 |
| --- | --- | --- |
| L0 查询 | 查询指标、实例状态 | 直接执行；RBAC 和审计仍生效 |
| L1 低风险变更 | 重试可逆任务、调整单一非生产参数 | 计划预览 + 有权限用户确认 |
| L2 中风险变更 | 生产扩缩容、配置发布 | 计划预览 + 双人审批 + dry-run/前置检查 |
| L3 高风险变更 | 删除、批量操作、不可逆数据动作 | 第一期禁用，仅给出 Runbook 建议 |

此外必须实施：环境隔离（生产默认更严格）、敏感数据脱敏、提示词注入防护、调用预算与频率限制、工具输出长度限制、审计关联 ID、失败自动停止，以及按资源类型配置的最大影响范围。

## 5. 分阶段实施路径

### 阶段 0：治理与 API 整备（第 1–2 周）

1. 从 OpenAPI 清点接口，给每个接口标注读/写、环境、资源范围、风险、回滚性和幂等性。
2. 选出 10–20 个高频只读场景，及 3–5 个低风险、可回滚写场景。
3. 补齐 Runbook、拓扑和告警说明的版本与权限元数据。
4. 制定统一的 AI 调用审计事件和“计划—确认—执行”状态模型。

交付物：工具 allowlist、风险矩阵、场景清单、审计字段规范。

### 阶段 1：只读 AI 助手（第 3–6 周）

1. 建设知识检索与只读工具调用。
2. 接入对话页，提供查询、告警解释、资源关联和排障建议。
3. 对每次回答展示事实来源、API 调用和不确定性提示。
4. 建立离线评测集：真实匿名工单、告警与标准答案。

验收：目标场景的事实准确率、权限拒绝正确率、无越权工具调用，以及人工可追溯率达到预设门槛。

### 阶段 2：人工确认的变更计划（第 7–10 周）

1. 实现工具注册表和策略执行网关。
2. 引入结构化变更计划、风险分级、前置检查和回滚说明。
3. 上线确认卡片；通过“计划快照 + 确认令牌”绑定审批与执行。
4. 先在测试/预发运行，再灰度开放少量生产 L1 场景。

验收：100% 写操作经过确认；计划与实际执行参数一致；失败可定位；越权、超范围和高危请求被可靠拦截。

### 阶段 3：受控自动化与持续优化（第 11–12 周及以后）

1. 将经验证的多步骤操作编排为声明式工作流。
2. 引入告警触发的“建议计划”，仍保留人工确认。
3. 基于审计与人工反馈优化提示词、知识库和工具描述。
4. 仅在有充分数据、回滚与治理能力后，针对极少数 L0/L1 场景评估自动执行。

## 6. 第一批建议场景

1. 资源健康巡检：跨 Redis、Kafka、MQ 等中间件查询容量、连接数、积压和错误率。
2. 告警解释：汇总告警、关联近期变更与日志，输出可能原因和 Runbook 步骤。
3. 排障查询：如“过去 24 小时某 Topic 的积压变化及相关消费者状态”。
4. 变更计划：如“为指定非生产 Topic 扩分区”或“对单个实例执行可回滚的配置调整”。
5. 执行回执：以自然语言总结执行结果、影响和需要人工跟进的事项。

## 7. 模型、数据与部署建议

- 模型层采用可替换适配器；云模型适合复杂推理，私有部署模型适合敏感环境或高频简单任务。
- 不将生产密钥、原始敏感日志或完整配置直接放入提示词；由工具按需返回最小必要字段。
- RAG 文档与工具执行日志分库、分权限存储；保留文档版本和回答引用。
- 先以单 Agent + 明确工具边界实现，不在第一期引入多 Agent 自主协作。

## 8. 质量指标

- 查询事实准确率、带依据回答率、人工采纳率。
- 工具调用成功率、计划生成成功率、确认后执行成功率、平均响应时间。
- 拒绝不安全/越权请求的正确率、写操作确认覆盖率、审计完整率。
- 告警 MTTA、MTTR 和人工操作耗时的变化；这些指标需与未使用 AI 的基线对比。

## 9. 测试与发布

1. 为每个工具构造正常、越权、超范围、缺参数、敏感信息和失败响应测试。
2. 用脱敏历史工单建立离线回归集；每次变更模型、提示词或工具描述都运行评测。
3. 在沙箱/预发做端到端演练，验证审批、幂等和回滚。
4. 按团队和场景灰度发布，并设置一键关闭 AI 写操作的开关。

## 10. 明确不在本期范围内

- 无人值守生产变更；
- 删除或不可逆的批量操作；
- 直接让模型访问数据库、集群控制面或未登记 API；
- 用聊天记录替代既有变更管理、审批或审计系统。
